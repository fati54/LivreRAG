## 6.1 Introduction

Après avoir vu l’importance d’une architecture antifragile (Chapitre 5), détaillons maintenant le cœur opérationnel : le **pipeline**.  
Un pipeline bien conçu ne se limite pas à coller un moteur vectoriel à un modèle : c’est une **chaîne organisée d’étapes spécialisées**, coordonnées par un orchestrateur.  

---

## 6.2 Vue d’ensemble

Un pipeline antifragile suit quatre grandes étapes : **ingestion → retrieval → génération → vérification**, sous la supervision d’un orchestrateur.

## 6.3 Étape 1 : Ingestion

L’ingestion est la **porte d’entrée** du pipeline.  
Elle consiste à transformer des données brutes en documents exploitables.

### Bonnes pratiques
- Normaliser les formats (PDF, Word, JSON, APIs).  
- Nettoyer le bruit (footers, doublons, OCR correct).  
- Extraire des métadonnées (date, auteur, version, source).  

### Erreurs courantes
- Parsing incomplet (ex. PDF scannés mal traités).  
- Absence de suivi des versions.  
- Manque de pipeline d’ETL clair.  

Une ingestion fragile = retrieval biaisé dès le départ.

---

### 6.3.1 L'ingestion en profondeur

L'ingestion "en profondeur" ne se limite pas à charger des fichiers : elle **structure, segmente, vectorise et gouverne** le corpus.  
Objectif : transformer des sources hétérogènes en **unités de connaissance fiables**, prêtes pour le retrieval.

#### 6.3.1.1 Objectifs et artefacts produits

- Texte nettoyé et normalisé (encodage, sections, tables, entêtes).  
- Métadonnées riches (source, date, version, droits, confidentialité).  
- Chunks **adressables** (IDs stables, offsets, doc_id).  
- Embeddings + index prêts à requêter (vecteurs, BM25).  

#### 6.3.1.2 Chunking : stratégies et compromis

**Quatre stratégies dominantes** :

| Stratégie | Idée | Quand l'utiliser | Limites |
|---|---|---|---|
| **Fixed-size** | Découpage fixe par tokens/caractères | Baseline rapide, documents homogènes | Peut couper le contexte en plein milieu |
| **Recursive** | Découper d'abord par structure (titres, paragraphes), puis affiner | Documents structurés (Markdown, HTML, DOCX) | Nécessite des heuristiques propres à chaque format |
| **Semantic** | Créer des frontières quand le sens change | Longs documents continus (notes, transcriptions) | Plus coûteux (embeddings) |
| **Document-aware** | Règles par type (table, code, section légale) | PDF structurés, code, tables | Demande un parser spécialisé |

**Impact de la taille des chunks (extraits chiffrés)** : résultats d'une évaluation RAG multi-corpus :

| Corpus (évaluation NVIDIA) | Taille/stratégie gagnante | Accuracy E2E | Note |
|---|---:|---:|---|
| FinanceBench | 1 024 tokens | 0.579 | Page-level proche (0.560) |
| Earnings-Call | 512 tokens | 0.681 | Contexte court mais dense |
| KG-RAG | 1 024 tokens | 0.804 | Page-level 0.790 |
| RAGBattlePacket | 1 024 tokens | 0.790 | Page-level non indiqué |

Conclusion pratique : la "bonne" taille dépend du type de documents **et** de la structure des questions.  
Sur des corpus juridiques (Plaide) et santé (MGEN), le gain vient souvent d'un **chunking document-aware** (articles, sections, annexes) plus que d'un simple ajustement de taille.

##### Overlap : pourquoi, combien, quand éviter
- **Pourquoi** : réduire les coupures de contexte au bord des chunks.  
- **Combien** : souvent **10-20%** suffit (ex. chunk 500 tokens, overlap 50-100).  
- **Quand éviter** : documents très courts, ou si vous faites déjà du **re-ranking** (l'overlap ajoute du bruit).

##### Chunking spécialisé par type de document
- **PDF structuré** : découper par titres + paragraphes; garder les numéros d'articles.  
- **PDF scanné** : OCR -> détection de blocs -> nettoyage agressif des artefacts.  
- **Markdown** : sections (`#`, `##`, `###`) + limites de code fences.  
- **HTML** : split par `<h1>…<h3>` puis par `<p>`.  
- **Tables** : chunk par ligne/colonne, stocker schéma + table complète.  
- **Code source** : chunk par fonction/classe; garder la signature avec la docstring.

##### Late chunking vs early chunking
- **Early chunking** : on découpe **avant** l'indexation (classique).  
- **Late chunking** : on indexe d'abord **au niveau document**, puis on recoupe **après** un premier retrieval.  

**Quand préférer le late chunking ?**  
- Corpus courts, mais documents très structurés (contrats, normes).  
- Quand la cohérence globale du document compte plus que la granularité fine.

##### Exemple Python (from scratch)

```python
from __future__ import annotations
from dataclasses import dataclass
from typing import List

@dataclass
class Chunk:
    doc_id: str
    chunk_id: str
    text: str
    start: int
    end: int


def simple_tokenize(text: str) -> List[str]:
    # Tokenisation simple (pour un usage réel, préférez un tokenizer dédié)
    return text.split()


def chunk_fixed(text: str, doc_id: str, size: int, overlap: int) -> List[Chunk]:
    tokens = simple_tokenize(text)
    chunks: List[Chunk] = []
    step = max(1, size - overlap)
    for i in range(0, len(tokens), step):
        window = tokens[i : i + size]
        if not window:
            break
        chunk_text = " ".join(window)
        chunks.append(Chunk(doc_id, f"{doc_id}-{i}", chunk_text, i, i + len(window)))
    return chunks


def recursive_split(text: str, separators: List[str], max_tokens: int) -> List[str]:
    # Découpage récursif: on split d'abord par gros séparateurs, puis on affine
    if max_tokens <= 0:
        raise ValueError("max_tokens must be > 0")

    def _split(block: str, seps: List[str]) -> List[str]:
        if len(simple_tokenize(block)) <= max_tokens or not seps:
            return [block]
        sep = seps[0]
        parts = block.split(sep)
        results: List[str] = []
        for part in parts:
            results.extend(_split(part, seps[1:]))
        return results

    chunks = _split(text, separators)
    # Re-grouper si nécessaire
    out: List[str] = []
    buf: List[str] = []
    for c in chunks:
        if len(simple_tokenize(" ".join(buf + [c]))) <= max_tokens:
            buf.append(c)
        else:
            out.append(" ".join(buf).strip())
            buf = [c]
    if buf:
        out.append(" ".join(buf).strip())
    return [c for c in out if c]


# Exemple d'usage
text = "# Article 1\nLe contrat est...\n\n# Article 2\nLe delai est de...\n"
seps = ["\n# ", "\n\n", "\n", ". "]
chunks = recursive_split(text, seps, max_tokens=120)
print(chunks[:2])
```

#### 6.3.1.3 Embeddings : du texte au vecteur

Un embedding est une **projection numérique** : on transforme une phrase en un vecteur dense qui capture le **sens** plutôt que la forme exacte.  
Deux textes proches en sens -> vecteurs proches en distance (cosinus, dot product).

| OpenAI `text-embedding-ada-002` | 1 536 | 49.25 | 0.10 | Oui (multilingue) |

Notes : les scores MTEB Retrieval proviennent de benchmarks publiés (voir sources). Les modèles open-source n'ont pas de coût API fixe mais un **coût d'infrastructure** (CPU/GPU + stockage).

##### Fine-tuning d'embeddings : quand et comment
- **Quand** : jargon métier, taxonomies propres, ou faibles recall/précision sur vos requêtes réelles.  
- **Comment** : entraînement contrastif sur paires *(question, passage)* et triplets *(positif, négatif)*.  
- **Signal minimum** : logs de recherche, clics, ou Q/A validées par experts.

##### Multilingual vs monolingual (cas français)
- **Multilingue** : couvre FR/EN/DE, utile pour corpus mixtes ou clients internationaux.  
- **Monolingue** : souvent meilleur sur un domaine spécifique, mais moins robuste hors FR.  

Recommandation : tester 1 modèle multilingue + 1 modèle francophone et **choisir sur métriques terrain**.

##### Quantization des embeddings (réduction des coûts)
- **Quantization 8-bit / 4-bit** : diviser la mémoire et accélérer la recherche.  
- **Product Quantization (PQ)** : compresser les vecteurs en codes courts.  
- **HNSW + PQ** : compromis qualité / vitesse / RAM.

from __future__ import annotations
from dataclasses import dataclass

@dataclass
class Price:
    input_per_m: float
    output_per_m: float


def cost_per_month(
    requests: int,
    prompt_tokens: int,
    output_tokens: int,
    model: Price,
) -> float:

#### 6.3.1.5 Gestion du cycle de vie documentaire

Un corpus vivant doit être **versionné, rafraîchi et gouverné**.

##### Ingestion incrémentale vs reindexation complète
- **Incrémentale** : détecter les nouveaux documents et ne reindexer que ce qui a changé.  
- **Complète** : utile après un changement majeur de format ou de modèle d'embedding.

##### Détection des changements (hash / diff / versioning)

```python
from __future__ import annotations
from dataclasses import dataclass
from typing import Dict
import hashlib

@dataclass
class DocMeta:
    doc_id: str
    sha256: str
    version: int


def content_hash(text: str) -> str:
    return hashlib.sha256(text.encode("utf-8")).hexdigest()


def should_reindex(doc_id: str, text: str, registry: Dict[str, DocMeta]) -> bool:
    new_hash = content_hash(text)
    old = registry.get(doc_id)
    return old is None or old.sha256 != new_hash
```

##### Caches : semantic cache, embedding cache, response cache

- **Embedding cache** : `hash(contenu) -> embedding` pour éviter les recomputations.  
- **Response cache** : question exacte -> réponse (avec TTL).  
- **Semantic cache** : similarité d'embeddings pour réutiliser une réponse proche.  

```python
from __future__ import annotations
from dataclasses import dataclass
from typing import List, Optional
import time
import numpy as np

@dataclass
class CacheEntry:
    query_emb: np.ndarray
    answer: str
    timestamp: float

class SemanticCache:
    def __init__(self, ttl_s: int = 7 * 24 * 3600, threshold: float = 0.92):
        self.ttl_s = ttl_s
        self.threshold = threshold
        self.entries: List[CacheEntry] = []

    def lookup(self, query_emb: np.ndarray) -> Optional[str]:
        now = time.time()
        for e in self.entries:
            if now - e.timestamp > self.ttl_s:
                continue
            sim = float(np.dot(query_emb, e.query_emb))
            if sim >= self.threshold:
                return e.answer
        return None

    def add(self, query_emb: np.ndarray, answer: str) -> None:
        self.entries.append(CacheEntry(query_emb, answer, time.time()))
```

##### TTL sur les chunks (réglementaire vs actualités)
- **Réglementaire** : TTL long (6-24 mois).  
- **Actualités** : TTL court (7-30 jours) + freshness boost.

## 6.4 Étape 2 : Retrieval

Le retrieval est le **moteur de recherche interne** du pipeline.  
C’est lui qui va sélectionner les documents les plus pertinents.

### Techniques
- **Vector search** : recherche par embeddings.  
- **Hybrid search** : combiner vecteurs + BM25.  
- **Re-ranking** : reclasser les résultats avec un modèle spécialisé.  

### Bonnes pratiques
- Choisir la bonne granularité (chunks ni trop petits ni trop gros).  
- Ajouter des filtres sémantiques et des métadonnées.  
- Surveiller la précision/recall via métriques.  

Retrieval robuste = moins d’hallucinations.

---

### 6.4.1 Évaluer un pipeline RAG en pratique

L’évaluation doit couvrir **deux niveaux** :  
1) la **qualité du retrieval** (est‑ce que je récupère les bons passages ?)  
2) la **fidélité de la réponse** (est‑ce que la génération respecte les sources ?)

#### Retrieval
Métriques usuelles : **Recall@K**, **nDCG@K**, **MRR**.  
Benchmarks utiles pour tester la robustesse : **BEIR**, **MS MARCO**, **KILT**, **HotpotQA**, **Natural Questions**.  

#### Génération
Métriques à surveiller : **faithfulness**, **exactitude**, **citation coverage**, **taux de refus**, **latence** et **coût**.  
Un outil pratique pour automatiser ces contrôles est **RAGAS** (évaluation basée sur LLM + heuristiques).

**Sources**

- [MS MARCO : dataset QA/retrieval](https://arxiv.org/abs/1611.09268)  
- [KILT : knowledge‑intensive tasks](https://arxiv.org/abs/2009.02252)  
- [HotpotQA : multi‑hop QA](https://arxiv.org/abs/1809.09600)

### 6.4.2 Retrieval avancé (au‑delà du simple vecteur)

Quand les requêtes deviennent complexes, les techniques suivantes améliorent fortement la qualité du retrieval :

- **Query rewriting / feedback génératif** : enrichir la requête avec un LLM pour récupérer plus de signal.  
- **HyDE** : générer un “document hypothétique” puis vectoriser ce document pour retrouver de vrais passages.  
- **ColBERT (late interaction)** : meilleure précision via matching token‑par‑token.  
- **SPLADE (sparse retrieval)** : combine la force du lexical et la robustesse neuronale.

## 6.5 Étape 3 : Génération

La génération correspond au **travail du LLM** : formuler une réponse en utilisant les documents trouvés.

### Bonnes pratiques
- Encadrer le prompt (instructions claires, citations obligatoires).  
- Limiter le rôle du modèle à l’**assemblage** et non à l’**invention**.  
- Utiliser des gabarits (templates de prompts).  

### Erreurs courantes
- Concaténer trop de documents (bruit + coûts élevés).  
- Laisser le modèle répondre librement sans contrainte.  

Une génération bien encadrée est le cœur de la crédibilité du pipeline.

---

## 6.6 Étape 4 : Vérification

La vérification est l’étape qui transforme une réponse “probable” en une réponse **fiable et gouvernée**.

### Techniques
- **Critic LLM** : un second modèle vérifie la cohérence de la réponse.  
- **Risk governor** : filtre de conformité (données sensibles, RGPD, biais).  
- **Auditabilité** : chaque réponse reliée à ses sources.  

C’est la **ceinture de sécurité** du pipeline.

---

## 6.7 L’orchestrateur

L’orchestrateur est le **chef d’orchestre** :  
- il coordonne les 4 étapes,  
- applique la gouvernance,  
- journalise chaque interaction,  
- gère les fallbacks et la redondance.

Sans orchestrateur, le pipeline est une suite de scripts.  
Avec orchestrateur, c’est une **infrastructure maîtrisée**.

### Exemple Python : orchestrateur minimal

```python
# orchestrator.py : Orchestrateur RAG modulaire
from dataclasses import dataclass
from typing import List, Optional
import yaml

@dataclass
class RAGResponse:
    answer: str
    sources: List[dict]
    confidence: float
    audit_trail: dict

class RAGOrchestrator:
    """Orchestrateur central du pipeline RAG antifragile."""
    
    def __init__(self, config_path: str = "pipeline_config.yaml"):
        with open(config_path) as f:
            self.config = yaml.safe_load(f)
        
        # Modules injectés (agnosticité)
        self.ingester = self._load_module("ingestion")
        self.retriever = self._load_module("retrieval")
        self.generator = self._load_module("generation")
        self.verifier = self._load_module("verification")
    
    def query(self, question: str, user_context: Optional[dict] = None) -> RAGResponse:
        """Pipeline complet : retrieval → génération → vérification."""
        
        # 1. Retrieval hybride
        documents = self.retriever.search(
            query=question,
            top_k=self.config["retrieval"]["top_k"],
            strategy=self.config["retrieval"]["strategy"],
        )
        
        # 2. Génération avec citations obligatoires
        raw_response = self.generator.generate(
            question=question,
            documents=documents,
            template=self.config["generation"]["prompt_template"],
            citations_required=self.config["generation"]["citations_obligatoires"],
        )
        
        # 3. Vérification (critic LLM + risk governor)
        verified = self.verifier.verify(
            response=raw_response,
            sources=documents,
            config=self.config["verification"],
        )
        
        if not verified.is_safe:
            # Escalade humaine ou réponse de fallback
            return self._handle_unsafe(verified)
        
        return RAGResponse(
            answer=verified.text,
            sources=verified.cited_sources,
            confidence=verified.confidence_score,
            audit_trail=verified.audit_log,
        )
    
    def _handle_unsafe(self, result) -> RAGResponse:
        """Gestion des réponses bloquées par le gouverneur de risque."""
        return RAGResponse(
            answer="Cette question nécessite une validation humaine.",
            sources=[],
            confidence=0.0,
            audit_trail={"blocked_reason": result.risk_flags},
        )

# Utilisation
orchestrator = RAGOrchestrator("pipeline_config.yaml")
response = orchestrator.query("Quel est le délai de prescription en droit du travail ?")
print(response.answer)
print(f"Sources: {len(response.sources)}, Confiance: {response.confidence:.0%}")
```

L’orchestrateur coordonne les 4 étapes sans connaître les détails d’implémentation de chaque module. C’est le principe de **modularité** en action.

## 6.9 Analogie : le pipeline comme organisme vivant

- **Ingestion = système digestif** : transformer la matière brute en nutriments exploitables.  
- **Retrieval = mémoire** : retrouver l’information pertinente.  
- **Génération = langage** : formuler une réponse intelligible.  
- **Vérification = système immunitaire** : détecter et corriger les erreurs.  
- **Orchestrateur = cerveau** : coordonner l’ensemble.  

Le pipeline antifragile se comporte comme un organisme vivant : chaque organe est spécialisé, mais c’est leur coopération qui crée la résilience.

---

## 6.10 Erreurs fréquentes et pièges

- **Mauvais découpage des chunks** : bruit, perte de contexte.  
- **Index non mis à jour** : réponses obsolètes.  
- **Prompts trop longs** : coûts explosifs et dépassements de tokens.  
- **Absence de vérification** : hallucinations validées sans contrôle.  

Les erreurs sont inévitables, mais un pipeline antifragile apprend à les corriger.

---

## 6.11 Monitoring et observabilité

Un pipeline antifragile doit être **observé en continu** :  

- **Logs centralisés** pour tracer chaque étape.  
- **Tableaux de bord qualité** : taux d’hallucinations, recall du retrieval, coûts.  
- **Alertes proactives** : détection de PII, dérive des performances, dépassements budgétaires.  
- **Boucles de feedback** : utiliser les erreurs pour ajuster ingestion, retrieval ou prompts.  

L’observabilité est la clé pour passer de la théorie à la pratique.

## 6.12 Exemple chiffré simplifié

- Corpus : 100 000 documents juridiques.  
- Retrieval hybride sélectionne 20 passages pertinents.  
- Génération assemble une réponse avec 5 citations.  
- Vérification par critic-LLM élimine 2 incohérences.  

Résultat : une réponse **fiable, sourcée et générée en moins de 3 secondes**, avec un coût maîtrisé.

## 6.13 Cas concrets

- **Santé** : ingestion de protocoles médicaux → retrieval hybride → génération encadrée → vérification par critic-LLM.  
- **Droit** : ingestion de jurisprudences → retrieval multi-index → génération avec citations obligatoires → auditabilité garantie.  
- **Support client** : ingestion de FAQ → retrieval filtré par contexte → génération adaptée au ton → vérification pour éviter les hallucinations.  

---

## 6.14 Comparaison avec les frameworks actuels

Beaucoup de frameworks actuels implémentent seulement : **ingestion + retrieval + génération**.  
La **vérification** et l’**orchestrateur** sont souvent absents.  

C’est la différence entre :  
- un pipeline de **démonstration** (rapide mais fragile),  
- et une architecture **antifragile** (robuste, traçable, souveraine).  

---

## 6.15 Conclusion et transition

L’anatomie du pipeline révèle une vérité simple :  
**chaque étape est un maillon critique**.  

Une ingestion fragile biaise tout le reste.  
Un retrieval faible augmente les hallucinations.  
Une génération non encadrée perd la crédibilité.  
Une absence de vérification supprime la confiance.  

Ce n’est pas un luxe, c’est une nécessité : un pipeline antifragile doit être conçu comme un **organisme complet**, avec un orchestrateur comme cerveau.
